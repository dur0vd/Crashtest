Входы и их точные SHA — [integration-inputs.json](integration-inputs.json);
отчёт чата — [handoffs/parallel-integration.md](handoffs/parallel-integration.md).

## Объединение

Три `merge --no-ff` в порядке physics → rules → graphics. Общих изменённых файлов
у веток нет, текстовых конфликтов не было. Число тестов сложилось аддитивно:
1115 (база) → 1282 → 1502 → 1529, сборка успешна после каждого шага.

## Как связаны порты

`src/integration/ports.ts` — единственное место создания портов:

| Функция | Назначение |
| --- | --- |
| `createPorts({monteCarlo?})` | `createPhysicsPort()` + `createRulesPort()`; в браузере Монте-Карло идёт в Web Worker (`src/integration/browser.ts`) |
| `runProject(project, ports)` | физика → правила на том же Timeline; при `unsupported/insufficient-data/error` физики правила не запускаются |
| `currentVersions()` | движок `0.3.0` (SemVer физика+правила), UI `0.2.0`, корпус — SHA-256 канонического JSON корпуса норм |
| `rulesMode(project)` | режим правил: без явного `educational` — `expert` (как у RulesPort) |

Потребители: кнопка ▶ (`src/main.ts`), рабочая область `mountWorkbench(…, {project, ports, versions})`,
проверка воспроизводимости и CLI `crashtest-verify` (`src/cli/bin.mjs`). Отдельной физики или
правил в UI нет: ▶ раньше вызывал `simulate()`/`analyze()` напрямую, теперь — порты.

Поведение ▶:

- кинематический режим: Timeline порта побитово равен прежнему `simulate()` на всех 79 пресетах;
- динамический режим: либо новое ядро для всех ТС, либо окно «Расчёт в выбранном режиме не
  поддерживается» с участниками и путями; кинематика не подставляется;
- новая ситуация/пресет из главного окна — явный учебный режим разбора; переключатель
  «Режим разбора» и «Модель движения» во вкладке «Среда». В экспертном режиме правовая оценка
  не показывается («Правовая оценка выключена»), в отчётах PDF/DOCX она выключена по умолчанию;
- результат сохраняется в проект с хэшем входов и версиями — его же проверяет CLI.

## Адаптер «физика → правила» (торможение)

Воспроизведённый разрыв схем: RulesPort принимает доказательство `expert.braking` вида
`inputs{actorId, observationId, brakingMode, t1, t2, t3}`, `result.stoppingDistanceRangeM`,
а PhysicsPort возвращал `yellowServiceStop`/`assessAvoidability` в другой форме. Без адаптера ни
один настоящий расчёт не становился доказательством для 6.14/10.1.

Для каждой связи `extensions.rules.expert.bindings[{actorId, recordId, observationId}]`, чьего
`recordId` ещё нет в результате физики, интеграционный порт:

1. берёт наблюдение (`project.evidence` или `PhysicsOutput.observations`):
   `yellow-stop-line` → служебное торможение, `collision-avoidance` → экстренное;
2. `v0` — скорость участника в кадре `values.frame` рассчитанного Timeline (м/с);
3. вызывает `physics.calculate('expert.braking', {mode: 'yellow' | 'observed', …})` с t1–t3/j из
   `extensions.physics.vehicles[id].braking` (и `jService` для жёлтого);
4. переносит диапазон пути `[min, max]` и значения t1–t3 в схему правил, сохраняя формулу,
   источники, предпосылки и исходный результат физики в `result.physics`.

Новых чисел адаптер не вводит. Без t3/j/источника расчёт не выполняется, а правила остаются
с неизвестностью. Изменения в чужих областях ради адаптера: режим `observed` в
`src/physics/port.ts` и `brakingMode: 'emergency'` для `collision-avoidance` в `src/rules/expert.ts`
(жёлтый по-прежнему только `service`).
