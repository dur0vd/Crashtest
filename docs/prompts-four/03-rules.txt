ПРОМПТ 3. Правила и правовая интерпретация

Рекомендуемая модель: Claude Opus 5.5.
Альтернатива: GPT-6 Astra high.

Репозиторий: https://github.com/dur0vd/Crashtest
Твоя ветка: codex/parallel-rules
Общая проверенная база: origin/codex/full-simulator-base-v2
Твоя рабочая копия: ../Crashtest-parallel/rules
Твой отчёт: docs/handoffs/parallel-rules.md
Зависимости: Нет веток-зависимостей. Можно запускать одновременно с двумя другими чатами.

Последнее указание пользователя: всего четыре чата. Первые три работают
ОДНОВРЕМЕННО и НЕ ЗАВИСЯТ от результатов друг друга. Четвёртый запускается
после них для подключения, проверки и объединения. Это заменяет старые
23 промпта, очереди веток и запреты начинать 07.2 без отдельной ветки 06.6.
Старые blocking-handoff описывают прежнюю схему, а не обязательство ждать её.

В общей базе уже есть 04–05, 06.1–06.3 и проверенное объединение парковки,
велосипедистов/СИМ и пассажиров. Повторная проверка общего кода: 1115 тестов
в 35 файлах, npm run build успешно. Это не означает юридическую полноту
или натурную валидацию: открытые ограничения перечислены в
docs/STATUS-AUDIT-2026-10-22.md и исходных handoff.
Не реализовывай эти модули заново; исправляй только воспроизведённые пробелы
своей области. Ядро 07.1 (27cf511) уже включено: Dugoff/силы/подшаг/параметры.
Его не нужно писать заново. В 07.2/08.1 пока подготовка и блокировки; ядро
ещё не подключено к маршрутам/общему simulate(). Это не готовые динамика сцены и удар.

1. Сначала git status, git log, git worktree list. Сохрани чужую работу.
   Используй свою ветку и отдельный worktree/клон. Не меняй рабочую папку другого
   чата. Не делай reset/rebase/force-push, не меняй main и общую базу.
   Если своя ветка уже есть, продолжи её историю с настройкой tracking;
   команды создания ниже относятся только к первому запуску.
2. Прочитай AGENTS.md и docs/codex/README.md, если появились, затем
   docs/FULL-SIMULATOR-REQUEST.md, docs/STATUS-AUDIT-2026-10-22.md,
   docs/PARALLEL-CONTRACT.md и src/parallel/contracts.ts. Старые документы
   не переопределяют новое разделение работы. Исходные детали ТЗ сохраняются,
   меняются ветки, порядок и назначение исполнителей.
3. Первые три чата не fetch/merge ветки друг друга для продолжения задачи.
   Работа идёт от общей базы с фиксированными границами. Для межмодульного
   обмена используй общий контракт, собственные реализации экспортируй из
   назначенного файла. Импорты несуществующего кода соседнего чата запрещены.
   Первые три чата не меняют contracts.ts: необходимое расширение описать
   в своём отчёте, сохранив рабочий адаптер к версии 1. Интегратор объединит
   реальные реализации; отсутствие соседней ветки не причина остановить чат.
4. Сохраняй совместимость сцен, известное/неизвестное, даты редакций,
   technical/rules/legal, trace с формулой, подстановкой, единицами, источниками
   и пределами метода. Неизвестное не равно false. Источники, лицензии,
   штрафы, медицинские коэффициенты и натурные данные не выдумывать.
   Конкретный TODO(legal-check)/TODO(source-check) не заменяет остальную работу:
   выполни всё, что доступно без неподтверждённого факта, и укажи ограничение.
5. Работай по внутренним проверяемым подэтапам и продолжай в ЭТОМ же чате до
   завершения всей своей области. После каждого законченного подэтапа —
   npm test и npm run build, отдельный коммит и push своей ветки. Не заканчивай
   всю задачу после одного маленького подпункта. После прерывания продолжай
   по своему отчёту и реальному git diff, не переделывай уже готовое.
6. Проверки должны быть независимыми: аналитика/измеренные треки/опубликованный
   пример, а не копирование ожидаемого значения из реализации. Изменённый UI
   проверить в Chromium. Существующие 1115 тестов и пресеты сохранить; снижение
   их числа или ослабление ожиданий требует конкретного обоснования.
7. Своя профильная документация и уникальный docs/handoffs/parallel-*.md:
   базовый SHA, что реально сделано, экспорты, команды/результаты, источники,
   ограничения, файлы за пределами своей области и что подключить интегратору.
   Не переписывай чужие handoff и общий каталог. Не записывай SHA коммита
   внутрь того же коммита как самоссылку: итоговый SHA дай в ответе.
8. Общие файлы трогать только по таблице владельцев в PARALLEL-CONTRACT.md.
   В общем UI физику/правила заменять заглушками нельзя; вычислительная
   недоступность должна быть явной, без нулей и вымышленных результатов.
   Двойники адаптеров допустимы в тестах интерфейса, не как расчёт в продукте.
9. Публиковать только свою ветку. Первые три чата не сливают соседей;
   четвёртый объединяет только три назначенные ветки в своей итоговой ветке.
   Main не менять, npm-пакет не публиковать, сервис не развёртывать.
   Коммиты «Этап NN: …» по исходному номеру, объединение — «Интеграция: …».
   В финале дать ветку, SHA, готовое, частичное, проверки и путь своего отчёта.

Команды первого запуска из отдельного клона/свободной рабочей папки:

git fetch origin refs/heads/codex/full-simulator-base-v2:refs/remotes/origin/codex/full-simulator-base-v2
git worktree add -b codex/parallel-rules ../Crashtest-parallel/rules origin/codex/full-simulator-base-v2
cd ../Crashtest-parallel/rules

ТВОЯ ЗАДАЧА

Твоя область — оставшиеся ПРАВИЛА И ПРАВОВАЯ ИНТЕРПРЕТАЦИЯ.
Готовые 04–05, переезды/спецсигналы/маршрутные ТС, парковку, СИМ и пассажиров
не переписывать. Проверить их конкретные ограничения и закрыть только пробелы
с подтверждёнными источниками. Полная динамика и новый интерфейс делаются
в других чатах; для своего кода они не являются предварительным условием.

Владеешь src/rules/**, правилами src/analysis (кроме technical.ts),
traffic-control.ts, restrictions.ts, law/corpus/редакциями/данными норм
при необходимости подтверждённого исправления. Не меняй sim/physics,
Scene/normalizeScene, ui/editor/render/main или научные коэффициенты.
Новые факты света и специальных условий храни в extensions.rules;
существующие Actor.stopContext/mobilityContext/passengers/WarningContext
переиспользуй, не заводи копии уже известных фактов.
Публичный вход: src/rules/port.ts → createRulesPort(): RulesPort.

1. Основной отсутствующий подпункт — 06.6: раздел 19, ближний/дальний свет,
   ДХО/противотуманные приборы, день/ночь/недостаточная видимость, ослепление,
   положения 7.1 об аварийной сигнализации. Состояние hazard брать из
   vehicleSignalAt/Waypoint.signal и готового warningContext; не создавать
   второй источник активности. Условия применимости и квалификацию выбирать
   по корпусу и дате, не приписывать одному расстоянию факт ослепления.
   Описать входы через describe(project), включая неизвестные состояния.
2. Оставшееся 06.5: возраст ровно 14, велозоны/номера знаков/8.4/3.35,
   льготы и конкуренция составов СИМ/мопеда 12.29/12.30; сверка первоисточников,
   дат и картинок, без льготы из ошибочного индекса. Закрыть непокрытые
   применимые абзацы 24: пассажиры/шлем/руль/буксировка/колонны/отражатели,
   велозона вне перекрёстка/повороты там, где есть достаточные наблюдения.
   Не переносить границы наблюдения из теста в законодательную норму.
3. Оставшееся 06.7: специальные условия 22.1–22.5/22.6 и субъекты/категории,
   посадка и сторона посадки, конкуренция общего/детского состава,
   организованные группы только по подтверждённым правилам и редакциям.
   Готовые детские возрастные границы и три состояния фактов сохранить.
   Не рассчитывать медицинский эффект защиты и не добавлять массу пассажиров
   повторно: этим занимается физика по своим явным данным.
4. Оставшееся 06.4/прочих готовых модулей: отдельная квалификация двери/ухода/
   ребёнка/мер вынужденной остановки; субъект и конкуренция специальных
   составов; известный город/дата. Исторические интервалы корпуса проверять
   по первоисточнику. Не закрывать TODO предположением и не повторять
   выполненные геометрические проверки парковки. Причинность не выводить
   автоматически из контакта с нарушающим стоящим ТС.
5. Экспертный режим: научный вывод отдельно от нормы/квалификации. Для 6.14
   и технической возможности использовать переданные PhysicsOutput/calculation
   с t1–t3, предпосылками и диапазонами. При отсутствии таких данных технически
   зависимый вывод остаётся неопределённым; сами алгоритмы норм проверяй
   независимо заданными наблюдениями/расчётными доказательствами. Не писать
   свой вариант тормозной/травматической формулы вместо порта физики.
6. Европротокол/ОСАГО для мобильного мастера: ст. 11.1, число ТС/вред/лимиты/
   разногласия по дате с источником, без имитации официального сервиса.
   П.22 ст.12 об ОСАГО — проверить точную редакцию/применимость до вывода
   о равных долях. Не выдавать процент вины. Содержание ст.25 профильного
   ФЗ и ст.204 УПК для шаблона заключения — сверить, указать необходимые
   реквизиты и ограничения, не изображать юридическую сертификацию отчёта.
7. Отчёт и безопасность: машинные результаты/ссылки/даты/предупреждения для
   RulesPort, JSON-совместимые факты и текстовые подсказки без DOM. Правовые
   рекомендации PRIVACY/оператор/согласие только по подтверждённым основаниям;
   реализация шифрования/редактора ПДн — чат графики.
8. Независимые тесты для применимых/неприменимых/неизвестных обстоятельств,
   возрастных/датовых границ, соблюдения без штрафа, конкуренции и причинности.
   Все ранее действовавшие нормы и разделение technical/rules/legal сохранить.
   Не обновлять весь корпус массовым непроверенным скачиванием: точечные
   изменения с URL/редакцией/свидетельством и проверкой санкций.

Новые подсказки/поля экспортируй через describe(project); состояние UI не
требуется для готовности правил. Применяй базовый Timeline и независимые
наблюдаемые треки, а проверенные научные данные принимай через общий контракт.
Доведи все доступные пункты, остальные пометь конкретным правовым пробелом.
Чат не должен завершиться после отчёта «жду физику» или создания пустого порта.
