Итоговое объединение веток симулятора

Рекомендуемая модель: GPT-6.1 Sol high в Codex.
Альтернатива: Claude Opus 5.5 в Claude Code.

ПРОМПТ

Репозиторий: https://github.com/dur0vd/Crashtest
Твоя ветка: codex/full-simulator-integration
База: origin/codex/full-simulator-base-v1
Отдельный worktree: ../Crashtest-worktrees/full-simulator-integration
Реестр задач: docs/prompts/branches.json
Главный отчёт: docs/INTEGRATION.md
Манифест зафиксированных входных SHA: docs/integration-inputs.json

Новое указание пользователя: объединить результаты отдельных веток в конце.
Сначала прочитай AGENTS.md и docs/codex/README.md, если появились, затем
полный исходный запрос, docs/REMAINING-WORK.md, docs/BRANCH-WORKFLOW.md,
реестр branches.json и handoff всех реализованных задач. Сохрани даты норм,
technical/rules/legal, неизвестность фактов, trace, оригиналы и лицензии.

1. Проверить git status/log и git worktree list, не менять чужие worktree.
   Для первого запуска:

   git fetch origin refs/heads/codex/full-simulator-base-v1:refs/remotes/origin/codex/full-simulator-base-v1
   git worktree add -b codex/full-simulator-integration ../Crashtest-worktrees/full-simulator-integration origin/codex/full-simulator-base-v1
   cd ../Crashtest-worktrees/full-simulator-integration

   Если ветка уже существует, продолжить её историю в отдельном worktree;
   если есть только удалённая — получить её и настроить tracking. Не начинать
   существующее объединение заново, не использовать reset/rebase/force-push.
   main, базовую ветку и ветки исполнителей не менять.

2. Инвентаризация ДО слияний. Для каждой задачи 1–20 из branches.json получить
   назначенную удалённую ветку явным fetch refs/heads/NAME:refs/remotes/origin/NAME
   и зафиксировать текущий SHA. Для 21 получить ветку, если она существует
   и готова: учебный режим необязателен. Одинаковая база должна содержать
   af0cdccb2488be7ec0e7d6e3aaba1ff97a939df5. Отсутствующая ветка не равна готовой
   задаче. Сам факт существования ветки или совпадения commit prefix также
   не доказывает готовность. Не создавать пустые ветки для заполнения списка.

3. В каждом зафиксированном tip читать handoff именно через git show SHA:PATH.
   Сверить номер, ветку и baseSha (равен общему зафиксированному базовому SHA),
   implementationStatus, blocking, test/build, ограничения и необходимые контракты. Для каждого dependencies[].sha
   проверить git merge-base --is-ancestor DEP_SHA TASK_SHA и сопоставить его
   с реестром. Также проверить, что общий базовый SHA является предком
   каждого TASK_SHA через git merge-base --is-ancestor. На разных ветках могли
   проверяться разные версии зависимости:
   записать это, оценить последующие изменения и обязательно проверить их
   совместимость в итоговой сборке. Нельзя считать старую проверку проверкой
   более нового контракта. Не доверять одному только зелёному полю JSON:
   посмотреть diff, реальные тесты и правдоподобие заявленных результатов.

4. Сохранить снимок входов в docs/integration-inputs.json: baseSha, task,
   branch, выбранный sha, зависимости и их SHA, статус, включён/пропущен и
   причина. Во время текущего прохода не менять выбранные tip незаметным fetch.
   При осознанном обновлении одного tip обновить манифест и повторить затронутые
   проверки. Для отсутствующих/блокированных обязательных задач перечислить,
   что осталось; полезную готовую часть можно объединить, но результат должен
   иметь статус «неполное объединение». Не дописывать молча крупный отсутствующий
   этап вместо его автора и не выдавать отсутствующую проверку за выполненную.

5. Объединять выбранные ГОТОВЫЕ SHA задач в топологическом порядке из реестра
   обычным git merge --no-ff --no-commit SHA, затем проверки и git commit.
   Не squash, cherry-pick или rebase:
   истории зависимостей должны сохраняться, уже включённые предки повторно
   не дублировать. Держать один незавершённый merge за раз. Конфликты разрешать
   по контрактам и исходным требованиям, не выбирать целиком ours/theirs.
   Особое внимание: scene/normalizeScene, actorSpec/массы, sim/physics,
   analysis/legal, сигналы/пассажиры/парковка, UI/editor/render/presets,
   локальное хранение, форматы evidence/project/report и package lockfile.
   Содержательные исправления совместимости фиксировать отдельными коммитами
   «Интеграция: …» с объяснением; сохранность исходных данных обязательна.

6. После каждого существенного merge проверить типы и затронутые тесты;
   npm test и npm run build должны пройти перед фиксацией принятого подэтапа.
   При конфликтном merge сначала устранить конфликт и проверить результат,
   затем завершить merge. Проверить все пресеты, оба режима физики, неизвестные
   факты и миграции старых сцен. UI пройти в Chromium, включая мобильный режим.
   Проверки нового CLI, validation-report, Node/Chromium determinism и security
   запускать, если они действительно реализованы; отсутствие команды отметить,
   а не заменить выдуманным результатом. CI на удалённой платформе не считать
   пройденным по одному локальному запуску; проверить фактическое выполнение.

7. Финальная приёмка по исходному запросу: какие требования выполнены полностью,
   частично или отсутствуют; branch/SHA, источники, ограничения и evidence
   проверок. Собрать реестр TODO(legal-check)/TODO(source-check) реальным rg
   по исходникам/документации с исключением build/dependencies/.git; отделить
   инструкции, цитирующие метку, от действительных незакрытых вопросов.
   Обновить docs/FULL-SIMULATOR.md, README и docs/INTEGRATION.md.
   Сохранять честный статус «не валидировано», если нет лицензированных данных.
   Не заявлять юридическую или физическую полноту на основании одних тестов.

8. В конце ещё раз npm test и npm run build на итоговом дереве; проверить
   чистоту статуса, отсутствие случайных временных файлов и сохранность всех
   исходных handoff. Коммит итоговой документации/исправлений, затем:

   git push -u origin codex/full-simulator-integration

   Не сливать в main, не удалять ветки исполнителей, не публиковать npm и
   не развёртывать сервисы. Задача — готовая проверенная ветка для просмотра.
   В финале дать итоговый SHA/ветку, все включённые/пропущенные задачи,
   результаты проверок, конфликтные решения, ограничения и оставшуюся работу.

После опубликованного объединения можно запустить 22-independent-review.txt.
Если отчёт проверки уже существует и относится к текущему проверенному коду,
учесть его находки; новые исправления требуют проверки актуальности reviewedSha.
Саму ветку проверки не включать как обязательную зависимость этого задания:
иначе образуется цикл. Отчёт проверки не является реализацией отсутствующего этапа.
